MERIDIAN TRANSFER
DETAILED PROJECT EXPLANATION
========================================

Prepared from the current project files and recorded verification reports.
Project date in the records: 23 September 2026.


1. PROJECT OVERVIEW
-------------------

Meridian Transfer is a fictional cybersecurity investigation and Capture the
Flag (CTF) platform created for IE3132 - Penetration Testing.

The project uses a customized CTFd 3.8.7 installation running in Docker on an
Ubuntu 24.04 virtual machine. Participants investigate a fictional research
cooperative preparing a research-data handover. Each challenge presents a
different security or forensic problem and requires the participant to inspect
evidence, reason about it, and submit a flag.

The platform currently contains five implemented stages:

  MT-01  Digital Footprints                 OSINT / Reconnaissance  100 points
  MT-02  The Amended Contact Sheet          Steganography           150 points
  MT-03  Dispatch Window                    Cryptography            200 points
  MT-04  Release Register Exception        Web Security             250 points
  MT-05  The Offset in the Handover Log    Digital Forensics         300 points

The current implemented total is 1,000 points. A sixth stage, MT-06 -
Reconcile the Transfer Ledger, is planned but has not been implemented.

The project is designed as a local, synthetic, offline training environment.
It does not depend on real targets, real people, personal data, or Internet
research to solve the challenges.


2. CURRENT IMPLEMENTATION STATUS
--------------------------------

MT-01 is recorded as IMPLEMENTED AND VERIFIED. Its build, solver, public
release, CTFd integration, participant submission, recovery, and regression
checks passed.

MT-02, MT-03, MT-04, and MT-05 are recorded as IMPLEMENTED BUT NOT VERIFIED.
This means their automated technical checks and CTFd tests pass, but the
required independent human participant review has not yet been completed.
The project does not falsely treat the blank review templates as approval.

MT-04 also has a documented network limitation: the challenge container is
isolated from the CTFd database and cache networks, but strict outbound
egress blocking has not yet been applied with a host firewall rule.


3. CTFd PLATFORM AND DEPLOYMENT
-------------------------------

The competition platform is based on the official CTFd 3.8.7 release at a
pinned Git commit. Pinning the exact release and commit keeps the deployment
reproducible and prevents unexpected upstream changes.

The main local platform runs as three Docker services:

  - ctfd: the web application and challenge platform;
  - db: the CTFd database;
  - cache: the CTFd cache service.

The database and cache do not publish host ports. The CTFd web service is
bound to loopback and, when available, the first private VM IPv4 address. The
Nginx service is disabled in the local override because the deployment uses
direct local HTTP access.

The deployment scripts check the Docker and Compose environment, prepare the
official CTFd source, create protected secrets, build or reuse the CTFd image,
start the services, wait for HTTP readiness, and run functional checks.

The normal local URL is:

  http://127.0.0.1:8000

The recorded VM URL is:

  http://10.0.2.15:8000

Host access is not automatically guaranteed because a VirtualBox NAT guest
usually needs explicit port forwarding. The project documentation correctly
warns that any future forwarding should be limited to the local lab.


4. SECRET AND DATA PROTECTION
-----------------------------

Sensitive operational files are kept in the ignored .secrets/ directory.
These include administrator credentials, the CTFd SECRET_KEY, service secrets,
diagnostic logs, and private functional-test results.

The secret files are created with restrictive permissions. The CTFd secret key
is passed through an environment file and a supported file fallback. The
upstream CTFd source and its database/uploads are excluded from the project
repository.

Author-only flags, solutions, private evidence, and training credentials are
stored outside public challenge packages and are excluded by .gitignore.

The public release validators check that private answers do not accidentally
appear in published evidence.

-----------------------------------------

The project replaces the generic participant-facing presentation with a

The homepage presents the theme with the message:

  Every handover leaves a trace.

It introduces the fictional case, provides registration and sign-in actions,

The custom interface includes:

  - a dark navigation bar with Meridian Transfer branding;
  - green accent colours and a light evidence-file visual style;
  - styled challenge cards, buttons, forms, and submission components;
  - mobile-responsive layouts and collapsible navigation;
  - dark-theme variables;
  - visible keyboard focus states;
  - role-specific navigation and account information.

Guests see the public homepage, sign-in, and registration controls.

The custom navbar is mounted read-only into CTFd. Homepage and configuration
changes are applied through CTFd configuration and page APIs so the pinned

6. REGISTRATION AND ACCESS POLICY
---------------------------------

Registration is public and does not require registration codes, user caps, or
email verification in this local training deployment.

Challenge viewing, challenge APIs, attachments, and submissions require a
signed-in participant. Administrator routes and protected APIs require the
administrator role.

The custom challenge-signin plugin adds an extra attachment rule. CTFd can
normally allow a signed download token to retrieve a challenge file without a
current session. The plugin checks that the requester has a live session before
serving challenge attachments.

Recorded access checks passed for:

  - anonymous administrator access being blocked;
  - participant access to administrator functions being blocked;
  - registration and participant login;
  - role escalation being blocked;
  - administrator login;
  - logout restoring access to registration.


7. MT-01 - DIGITAL FOOTPRINTS
-----------------------------

Domain: OSINT / Reconnaissance
Difficulty: Easy
Value: 100 points
Expected solve time: 10-15 minutes

MT-01 is an introductory evidence-correlation challenge. The participant
receives one text attachment containing four synthetic, public-style records.
The records describe six possible contributor aliases.

The player must identify the one alias satisfying all three conditions:

  - the correct workstream;
  - the required activity window;
  - confirmation of the relevant briefing conditions.

Each individual clue, and some pairs of clues, leave plausible decoys. The
intended solution is to create a candidate list for each condition and take the
intersection of all lists.

The answer is submitted in the MT-01 flag format using the surviving alias.

The implementation includes:

  - a deterministic evidence builder;
  - a public UTF-8 text attachment;
  - a SHA-256 integrity manifest;
  - a private author flag and solution;
  - a reference solver;
  - unique-solution and ambiguity checks;
  - public-leak validation;
  - participant download and submission tests;
  - recovery checks.

Recorded checks confirm that the wrong flag is rejected, the correct flag is
accepted for 100 points, and a duplicate submission does not award additional
points.

This is the only stage currently recorded as fully implemented and verified.


8. MT-02 - THE AMENDED CONTACT SHEET
------------------------------------

Domain: Steganography
Difficulty: Easy
Value: 150 points
Expected solve time: 15-20 minutes

MT-02 uses a synthetic 1080 x 720 RGB PNG. A textual metadata clue identifies
the relevant hiding method. The flag is hidden in the image pixels rather than
being written plainly in the public files.

The extraction format is precisely defined:

  1. Read the pixels in row-major order.
  2. Take the least significant bit of each red-channel value.
  3. Interpret the first 32 bits as an unsigned big-endian payload length.
  4. Read the payload bits most-significant-bit first.
  5. Decode the resulting bytes as UTF-8.

The participant must also verify the PNG checksum and inspect its metadata.
The challenge teaches the difference between visible image content, metadata,
and pixel-hidden information while preserving the integrity of a lossless file.

The implementation includes a deterministic PNG builder, an extraction solver,
metadata validation, checksum validation, public-release validation, unit
tests, CTFd integration, participant tests, and recovery checks.

The recorded report shows that the technical implementation passes. Independent
participant review by Member 03 remains pending.


9. MT-03 - DISPATCH WINDOW
--------------------------

Domain: Cryptography
Difficulty: Moderate
Value: 200 points
Expected solve time: 20-30 minutes

MT-03 provides a ciphertext, a release notice, and a SHA-256 manifest. The
ciphertext has two reversible layers:

  1. ASCII letters were shifted with a Caesar transformation.
  2. The shifted text was encoded with Base64.

The release notice supplies the date clue used to derive the Caesar shift. The
participant must identify Base64 as an encoding layer, decode it, derive the
shift from the release day, and shift the letters backward.

The challenge teaches the distinction between encoding and encryption, modular
arithmetic, case-preserving ASCII transformations, contextual key derivation,
and the importance of reversing layered transformations in the correct order.

The implementation includes deterministic generation, strict Base64 handling,
round-trip tests, wrong-key and wrong-order tests, invalid/truncated input
tests, a public-only reference solver, checksums, CTFd integration, browser
tests, and recovery validation.

The recorded report shows 28 of 28 unit tests passing and successful participant
integration. Independent review by Member 03 remains pending.


10. MT-04 - RELEASE REGISTER EXCEPTION
--------------------------------------

Domain: Web Security
Difficulty: Moderate
Value: 250 points
Expected solve time: 25-35 minutes

MT-04 is a separate Flask/Gunicorn web application running on loopback:

  http://127.0.0.1:8084

The CTFd platform stores the score, but the vulnerable release portal is a
separate service with a separate SQLite seed and Docker network.

Participants log in with synthetic training credentials and inspect release
records. The normal record route verifies ownership. The export route verifies
that the user is logged in but intentionally omits the ownership comparison.

This is an Insecure Direct Object Reference (IDOR). A participant can use an
in-scope record ID to request an export belonging to another account. The
intended lesson is that authentication identifies a user, while authorization
must also confirm that the user is allowed to access the requested object.

The project also includes a fixed variant that restores the ownership check.

The service is hardened as a local training container with:

  - a separate Docker bridge network;
  - no CTFd database or cache network membership;
  - no Docker socket or host-secret mount;
  - non-root UID/GID 10001;
  - a read-only root filesystem;
  - a read-only SQLite seed;
  - dropped Linux capabilities;
  - no-new-privileges;
  - CPU, memory, and process limits;
  - loopback-only host publishing by default;
  - CSRF protection on login and logout;
  - security response headers.

Recorded checks include 24 unit tests, 9 live HTTP tests, vulnerable/fixed
comparisons, CTFd wrong/correct/duplicate submissions, database/cache
separation, Docker-socket absence, resource-limit checks, and three recovery
cycles.

The remaining limitation is outbound egress. The service can make outbound
connections and can reach the VM host binding under the current Docker setup.
The project documents a future Docker-aware host firewall rule but does not
apply it automatically.

Independent review by Member 02 remains pending.


11. MT-05 - THE OFFSET IN THE HANDOVER LOG
-------------------------------------------

Domain: Digital Forensics
Difficulty: Moderate-Hard
Value: 300 points
Expected solve time: 30-45 minutes

MT-05 is the most involved evidence-correlation challenge currently built.
Participants receive an offline ZIP containing:

  - web_access.log;
  - application_audit.csv;
  - browser_history.sqlite;
  - schema_guide.txt;
  - case_context.txt;
  - EVIDENCE_SHA256SUMS.

The outer ZIP also has a public SHA-256 manifest.

The three evidence sources represent time differently:

  - application audit: YYYY-MM-DD HH:MM:SS+05:30;
  - web access log: DD/Mon/YYYY:HH:MM:SS +0000;
  - browser history: Unix epoch milliseconds in UTC.

The player must normalize the timestamps and identify exactly one completed
restricted export supported by all three sources.

The matching rules require:

  - the correct restricted record family;
  - an application action of export with completed status;
  - an event within the inclusive/exclusive investigation window;
  - a matching successful web GET export request;
  - matching event and record identifiers;
  - browser export corroboration within 60 seconds, inclusive.

The dataset contains 49 audit rows, 49 web rows, and 48 browser rows. Decoys
include failed or cancelled actions, normal views, mismatched identifiers,
boundary events, duplicate timestamps, failed HTTP responses, and missing or
late browser visits.

The answer is derived rather than stored literally. The participant creates:

  event_id|YYYY-MM-DDTHH:MM:SSZ|record_id

The value is encoded as UTF-8, hashed with SHA-256, and reduced to the first 16
lowercase hexadecimal characters before being wrapped in the MT-05 flag format.

The implementation includes two independently structured solvers. One uses
dictionary joins and the other uses an in-memory SQL join. Their agreement
checks the event selection, normalized timestamp, canonical value, bytes, and
hash result.

Recorded checks include 40 unit tests, manifest and archive validation, SQLite
read-only checks, timestamp boundary tests, solver agreement, public leak checks,
participant downloads and submissions, recovery cycles, and regressions against
the previous four stages.

Independent review by Member 02 remains pending.


12. TESTING AND VERIFICATION
----------------------------

The project tests multiple layers of correctness rather than checking only
whether a script runs.

Challenge-level checks verify deterministic generation, correct extraction or
decryption, unique solutions, decoy rejection, malformed-input handling,
timestamp boundaries, canonical serialization, and exact flag derivation.

Release checks verify checksums, expected file inventories, absence of private
answers from public packages, and restoration after temporary mutations.

Platform checks create synthetic participant accounts and exercise the real
CTFd workflow: registration, login, attachment downloads, wrong submissions,
correct submissions, score changes, duplicate submissions, and preserved solve
records.

Browser checks cover desktop and mobile layouts, navigation, registration,
sign-in/sign-out, role restrictions, challenge visibility, attachment downloads,
submission, and JavaScript errors.

Regression checks confirm that later integrations do not change earlier
challenge values, visibility, attachments, configuration, or correct-submission
records.

The saved reports record passing browser/UI and access checks for all five
implemented stages.


13. RECOVERY AND REPRODUCIBILITY
--------------------------------

Each stage has author tools, public-release validators, reference solvers, and
recovery guidance.

Recovery is intentionally performed on temporary working copies wherever
possible. A mutation is introduced, the checksum is expected to fail, the
temporary copy is removed, and the baseline is rebuilt and checked again.

MT-04 can be reset without deleting the CTFd platform or participant solves.
Its reset rotates the service session secret, invalidating old target sessions.

MT-05 records byte-identical repeated archives on the tested Python, SQLite,
zlib, and operating-system toolchain. The documentation correctly explains
that binary identity across different library versions is not guaranteed.

The integration scripts are designed to reuse existing challenge records and
preserve challenge IDs, attachments, and solve history rather than creating
duplicates during repeated setup.


14. REPOSITORY ORGANIZATION
---------------------------

platform/
  Deployment helpers, CTFd integration, UI customization, access checks,
  browser tests, participant functional tests, and the custom attachment
  session guard.

challenges/
  One directory per stage containing specifications, public evidence, author
  builders, reference solvers, validators, service code, and tests.

review/
  Participant-only independent-review packages, checksums, and blank review
  result templates.

.secrets/
  Ignored credentials, secret keys, diagnostic logs, and private execution
  records. This directory is not part of the public project release.

.gitignore
  Excludes private answers, secrets, the upstream CTFd clone/data, generated
  databases, and other non-public material.
